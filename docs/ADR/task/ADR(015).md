# ADR 015: AmbiOS User Interaction and WebMCP Entry Strategy

> **Deployment correction (2026-09-03).** The current deployment boundary is Vercel Next.js plus two Hono Cloudflare Workers. References below to one Cloudflare deployment serving the complete app are historical and superseded by ADR-021; retain them as evidence of the earlier decision path.

**Status:** Accepted for the WebMCP Challenge; review after Phase 0  
**Date:** 2026-09-01  
**Deciders:** AmbiOS AI project team  
**Owner:** AmbiOS AI project team  
**Scope:** User interaction surfaces, WebMCP exposure, deployment topology, and hackathon entry strategy

## Decision Summary

AmbiOS will be positioned as a **governed action layer for AI-powered work**, not as another general-purpose chatbot or browser extension.

For the WebMCP Challenge, the canonical entry point will be one publicly accessible Vercel deployment serving the complete Next.js AmbiOS application and explicitly registering the `ambios.*` WebMCP tools on the page. Hono Cloudflare Workers provide the API and execution backend. ChatGPT Desktop's in-app browser will be the primary demonstration path. Chrome with WebMCP enabled will be the fallback and independent verification path. The direct AmbiOS UI will remain fully usable without an AI agent.

ChatGPT supplies conversational intent and reasoning. The browser supplies page context and the WebMCP bridge. AmbiOS remains the authority for identity, tenant scope, permissions, guardrails, approvals, execution, verification, and audit history.

## Context

AmbiOS AI combines an operational dashboard, an AI conversation surface, integrations, agent actions, human approval, and WebMCP tools. The platform must make the same governed capabilities understandable and safe across multiple entry surfaces:

- AmbiOS's own web dashboard.
- ChatGPT Desktop and its in-app browser.
- Chrome with WebMCP enabled.
- Future direct MCP/API or other agent runtimes.

The project is also being submitted to the WebMCP Challenge. The judging path therefore has different constraints from the long-term product architecture:

- Judges need a public URL they can open without local setup.
- The page itself must expose discoverable WebMCP tools.
- The first useful interaction must be clear and safe.
- The demo must show meaningful collaboration between a human and an agent.
- The repository, live page, and short video must explain the implementation independently.
- The judging experience must not depend on production credentials or a fragile multi-service onboarding sequence.

The repository already establishes the main infrastructure decisions:

- Cloudflare Workers and Pages are the primary runtime ([ADR 002](./ADR%28002%29.md)).
- D1 stores operational state, with KV, R2, and Queues used for supporting concerns ([ARCHITECTURE.md](../../../ARCHITECTURE.md)).
- Declarative guardrails govern sensitive actions ([ADR 007](./ADR%28007%29.md)).
- Actions are recorded in an append-only audit log ([ADR 008](./ADR%28008%29.md)).
- WebMCP tools use the `ambios.*` namespace ([ADR 013](./ADR%28013%29.md)).
- Phase 0 focuses on a context-aware incident hot-fix workflow ([ADR 014](./ADR%28014%29.md)).

The local browser evidence at [WebMCP(1).png](../../../public/assets/screenshot/WebMCP%281%29.png) shows that the AmbiOS page at `localhost:3000` registers tools successfully: Chrome DevTools displays an Application → WebMCP panel with available `ambios.*` tools. This proves browser-level discovery and registration, but not yet successful invocation on the deployed Cloudflare URL. The same screenshot also shows a workspace-storage/D1 configuration error, which must be resolved before backend-dependent tools can be considered demo-ready.

## Product Positioning

AmbiOS is the governed action plane between user intent, agents, and operational systems.

> **AmbiOS helps people and agents understand context, propose safe actions, obtain approval when required, execute within policy, verify outcomes, and preserve proof of what happened.**

This positioning creates a clear division of responsibility:

| Layer | Primary responsibility | Must not own |
| --- | --- | --- |
| Human | Intent, judgment, approval, exception handling | Hidden automation decisions |
| ChatGPT or other agent | Conversation, reasoning, planning, tool selection | Final authorization or secret custody |
| Browser/WebMCP | Page context and capability discovery | Security enforcement |
| AmbiOS UI | Context display, approval UX, activity visibility, configuration | Unbounded provider access |
| AmbiOS Worker/API | Authentication, authorization, policy, execution, verification, audit | Trusting browser-provided claims |
| Provider adapters | Bounded calls to Cloudflare, GitHub, Nango, and other systems | Cross-tenant policy decisions |

The browser's WebMCP schema is a discovery and usability contract. It is never a security boundary. Every API route repeats server-side validation, organization scoping, permission checks, guardrail evaluation, and audit requirements.

## Interaction Topology

```text
Human
  │
  ├── AmbiOS web dashboard
  ├── ChatGPT Desktop / in-app browser
  ├── Chrome with WebMCP enabled
  └── Future direct MCP/API clients
          │
          ▼
Public Cloudflare AmbiOS application
  ├── Human UI and chat surface
  ├── WebMCP feature detection
  ├── Explicit `ambios.*` registration
  └── Same-origin credentialed requests
          │
          ▼
Cloudflare Worker / Next.js server runtime
  ├── Session and tenant resolution
  ├── Zod/request validation
  ├── RBAC and capability checks
  ├── Guardrail and budget evaluation
  ├── Human approval state machine
  ├── Bounded action execution
  ├── Result verification
  └── Append-only audit record
          │
          ├── D1: organizations, incidents, actions, docs, integrations
          ├── KV: short-lived approval state
          ├── R2: artifacts where required
          ├── Queues: durable asynchronous jobs
          └── Provider adapters / Nango / secret bindings
```

The preferred request path is same-origin:

```text
Agent → WebMCP tool → browser fetch with credentials → AmbiOS API route
      → authentication → tenant scope → guardrails → approval/execution
      → verification → audit → structured tool result
```

This preserves the existing authentication and deployment model and avoids introducing a second public control plane during the hackathon.

## Entry Surface Strategy

### 1. AmbiOS web UI — canonical product surface

The AmbiOS dashboard is the canonical user experience. It must remain useful when WebMCP is unavailable, disabled, or unsupported. It owns:

- Workspace and incident context.
- Action proposals and risk presentation.
- Approval and denial controls.
- Activity and audit history.
- Documentation proposals.
- Connector and integration status.

The UI is also the visible proof surface during the demo: a judge should be able to see the context, proposed action, approval state, result, and audit record without inspecting browser internals.

### 2. ChatGPT Desktop in-app browser — primary challenge path

ChatGPT Desktop's in-app browser is the primary entry path for the challenge because it provides the intended agent interaction surface and can discover tools exposed by the open AmbiOS page.

The expected experience is:

```text
Open AmbiOS → agent discovers `ambios.*` → user asks about an incident
→ agent reads context → agent proposes a hot-fix → AmbiOS requires approval
→ human approves in AmbiOS → agent invokes bounded action
→ AmbiOS verifies and reports the result
```

The first tool call should be read-only and require no destructive permission. The demo should not begin with a deployment, deletion, connector mutation, or mandatory OAuth flow.

### 3. Chrome with WebMCP enabled — fallback and verification path

Chrome is a supported fallback for reviewers and developers who want to validate the page outside ChatGPT. It must expose the same tools and enforce the same server-side policies.

Chrome is not a separate product integration. It is another compatible browser surface for the same deployed AmbiOS page and the same Worker/API contract.

### 4. Future direct MCP/API clients — expansion path

Direct MCP, API, or additional agent clients may be added after the challenge. They must call the same policy and execution services rather than creating parallel authorization logic.

### 5. Browser extension or native desktop client — deferred

No Chrome extension or native desktop client is required for the Phase 0 challenge entry. Those surfaces would introduce additional permissions, packaging, identity, update, and support concerns before the core WebMCP workflow is proven.

## WebMCP Contract

AmbiOS will explicitly register a curated, versioned set of tools under the `ambios.*` namespace from the deployed application page. Registration must be feature-detected and must fail gracefully when `document.modelContext` is unavailable.

### Tool classes

| Class | Examples | Default behavior |
| --- | --- | --- |
| Read-only context | `ambios.list_incidents`, `ambios.incident.get_incident_context`, `ambios.backend.get_status` | May execute after normal authentication and authorization |
| Analysis and policy | `ambios.incident.suggest_hotfixes`, `ambios.guardrails.evaluate_guardrails` | Returns recommendations and policy decisions; does not mutate state |
| Approval and workflow | Approval-status or action-preview capabilities | Creates or reads explicit approval state; does not bypass human approval |
| Mutating action | `ambios.incident.apply_hotfix`, `ambios.backend.deploy_service` | Requires server-side policy evaluation and approval when risk dictates |
| Evidence and follow-up | `ambios.audit.get_action_log`, `ambios.docs.get_doc`, `ambios.docs.propose_doc_update` | Reads or creates reviewable evidence; proposals remain reviewable |

### Registration rules

1. Register only tools implemented and tested on the deployed build.
2. Keep names, descriptions, schemas, and behavior synchronized.
3. Describe risk and approval requirements in tool descriptions, while enforcing them on the server.
4. Mark read-only and mutating behavior accurately.
5. Use strict input schemas with no unrecognized fields where practical.
6. Return structured, bounded results suitable for both the agent and human UI.
7. Use lifecycle-safe registration so development navigation or remounting does not create duplicate registrations.
8. Keep credentials and provider tokens out of tool arguments and browser storage.
9. Do not expose an internal vendor API as an unrestricted WebMCP surface.
10. Maintain one public contract; do not expose a second overlapping set of tools through an optional edge bridge without an explicit compatibility decision.

The number of registered tools must not be used as the primary success metric. The public documentation, implementation, and demo must agree on the actual deployed tool set.

## Canonical Challenge Workflow

The Phase 0 demonstration is **AmbiOS Safe Incident Hot-Fix**.

### Preconditions

- The public Cloudflare URL serves the real AmbiOS application.
- D1 binding and schema are available.
- A seeded demonstration organization, user context, service, incident, recent deployment, guardrail policy, budget, and audit history exist.
- The demo does not require the judge to connect real provider credentials.
- Any simulated provider operation is clearly labeled as simulated.

### Interaction sequence

1. The judge opens the public AmbiOS URL.
2. The page registers the curated WebMCP capabilities.
3. The agent performs one safe read-only call, such as listing incidents or reading backend status.
4. The agent reads the selected incident context.
5. The agent requests or receives hot-fix suggestions.
6. AmbiOS evaluates permission, environment, risk, budget, and rollback conditions.
7. A high-impact action returns an explicit approval-required result.
8. The human reviews the proposed action in the AmbiOS UI.
9. The human approves or denies the exact action.
10. If approved, AmbiOS executes a bounded action through the server-side adapter.
11. AmbiOS verifies the resulting state.
12. AmbiOS writes an immutable action record and, where applicable, a documentation proposal.
13. The UI displays the final status, evidence, and audit trail.

### Safety requirements

- No tool may treat an agent's request as proof of authorization.
- Production-impacting changes must not auto-submit merely because a form or tool is available.
- Approval must bind to the exact user, organization, action, target, parameters, and short expiration window.
- Approval must be single-use where the action is sensitive.
- Failed audit persistence must fail closed for mutating actions.
- Provider secrets must remain in server-side bindings or the approved integration owner, such as Nango.
- The demo must use a reversible, sandboxed, or deterministic simulated action unless a real action is explicitly bounded and safe.

## Cloudflare and OpenAI Sites Decision

### Cloudflare remains canonical for backend execution

Use the current split deployment described in [ADR 002](./ADR%28002%29.md) and [ARCHITECTURE.md](../../../ARCHITECTURE.md): Vercel owns the Next.js frontend and browser WebMCP registration; Hono Core and Connector/Execution Workers own same-origin-proxied APIs, D1 state, provider actions, and approval enforcement.

Cloudflare's optional WebMCP edge bridge may be evaluated as a development or compatibility aid. It is not the primary AmbiOS contract for this submission. Enabling it alongside explicit browser registration could cause duplicate tools, conflicting descriptions, or an unclear ownership boundary.

Cloudflare Browser Run is an optional remote testing harness. It can help validate discovery and invocation in an experimental browser session, but it is not required to host AmbiOS and is not a substitute for verifying the public judge URL.

### OpenAI Sites is optional, not required

OpenAI Sites is a possible hosting and sharing surface, but it is not automatically an MCP server and does not replace page-level WebMCP registration. AmbiOS should move to OpenAI Sites only if the complete application can deploy there without splitting the same-origin authentication and API model or duplicating the production control plane.

For the challenge, migrating to OpenAI Sites is not justified unless a compatibility test proves a material judging benefit. Vercel remains the canonical frontend deployment; Cloudflare Workers remain the canonical backend and execution runtime.

## Deployment and Verification Gates

The following gates define “working WebMCP” for AmbiOS:

### Gate A — browser registration

- The deployed page exposes `document.modelContext` when the browser supports WebMCP.
- The expected `ambios.*` tools appear in the browser's WebMCP inspection surface.
- Registration does not throw during page load or route navigation.

### Gate B — safe invocation

- A read-only tool can be discovered and invoked from ChatGPT Desktop.
- The request reaches the correct same-origin API route.
- The result is structured, tenant-scoped, and displayed to the agent.
- Tool activity or equivalent evidence shows the invocation and result.

### Gate C — governed mutation

- A mutating tool is discoverable but cannot bypass server-side checks.
- An unapproved high-risk request produces `APPROVAL_REQUIRED`.
- Approval is visible to and performed by the human in AmbiOS.
- The exact approved action can execute once and only within policy.

### Gate D — evidence and recovery

- The action is recorded in the audit log.
- The result is verified rather than assumed from the request response.
- Failure states are visible and do not report success.
- A rollback or safe recovery path is documented for the demonstrated action.

### Gate E — browser parity

- The same public URL and tool contract work in Chrome with WebMCP enabled.
- Unsupported browsers fall back to the direct AmbiOS UI without breaking the application.

### Gate F — submission readiness

- The public URL serves the application rather than only a health response.
- D1 bindings and schema are applied in the deployed environment.
- No secret or real provider credential is exposed.
- Repository instructions explain setup, demo flow, WebMCP implementation, and limitations.
- The short demo video shows the complete human-agent workflow.
- The challenge submission accurately describes what is live, simulated, and verified.

## Alternatives Considered

### Option 1: Cloudflare deployment with explicit AmbiOS WebMCP registration — chosen

**Advantages:**

- Matches the existing runtime and repository architecture.
- Keeps WebMCP, authentication, APIs, D1, approvals, and audit behavior aligned.
- Gives AmbiOS direct ownership of its public tool contract.
- Supports both ChatGPT Desktop and Chrome through the same page.
- Minimizes migration risk before the hackathon.

**Costs:**

- Requires reliable Cloudflare bindings and production verification.
- Requires AmbiOS to maintain registration lifecycle and tool schemas.
- The deployed page must be tested separately from localhost.

### Option 2: Cloudflare edge-injected WebMCP bridge

**Advantages:**

- Can add a bridge without changing as much application source code.
- May help test or adapt existing pages to WebMCP.

**Costs and reasons not chosen as primary:**

- Developer-preview behavior adds uncertainty.
- It can overlap with explicit AmbiOS registration.
- It makes ownership and debugging of the public tool contract less clear.
- It does not remove the need to verify backend authentication and execution.

### Option 3: OpenAI Sites as the primary deployment

**Advantages:**

- Potentially convenient sharing inside ChatGPT.
- May provide a direct distribution surface for a compatible app.

**Costs and reasons not chosen:**

- It is a hosting surface, not automatically an MCP/WebMCP implementation.
- Compatibility with the existing same-origin auth and Worker architecture must be proven.
- Migration introduces unnecessary deployment and debugging risk during the challenge.

### Option 4: Chrome extension or native desktop application

**Advantages:**

- More control over browser or desktop context.
- Potentially richer long-term workflows.

**Costs and reasons deferred:**

- Additional permissions, packaging, installation, identity, and maintenance burden.
- Distracts from proving the core WebMCP interaction.
- Not required by the challenge's primary judging path.

### Option 5: Separate MCP gateway or connector-specific agent layer

**Advantages:**

- Could support more clients and remote integrations over time.

**Costs and reasons deferred:**

- Risks creating a second policy and approval path.
- Increases operational and credential-management complexity.
- Should be added only after the shared AmbiOS action service is stable.

## Consequences

### Positive

- AmbiOS has a simple, memorable product identity.
- The challenge demo tells one complete story instead of presenting disconnected features.
- ChatGPT and Chrome become interaction surfaces rather than competing application architectures.
- Human approval remains visible and central for sensitive operations.
- All entry paths converge on one authorization, execution, verification, and audit model.
- The existing Cloudflare and D1 decisions remain useful rather than being replaced for presentation reasons.
- The direct UI remains usable when WebMCP is unsupported or disabled.

### Negative

- The public deployment must be treated as a first-class verification target.
- D1 binding/schema failures can make registered tools appear broken even when browser discovery works.
- The curated tool surface may expose fewer capabilities than the long-term platform vision.
- Some integrations and real provider actions must remain simulated or deferred for the challenge.
- ChatGPT and Chrome support may vary by browser version, account configuration, or enabled site-tool settings.

### Risks and mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Local registration works but production registration fails | Demo failure | Verify the public URL using the same browser inspection and read-only call sequence |
| D1 binding or schema is missing | Backend tools fail | Make D1 deployment and seeded data a release gate; fail clearly and fail closed |
| Duplicate tools from explicit registration and an edge bridge | Agent confusion | Use one primary registration path; enable the bridge only in an isolated compatibility test |
| Agent bypasses approval | Unsafe mutation | Enforce approval server-side and bind approval to the exact action |
| Tool count or names differ between docs and deployment | Reviewer distrust | Generate or manually reconcile one authoritative public tool list before submission |
| Demo depends on OAuth or provider credentials | Judge cannot complete flow | Seed a safe demo workspace and use clearly marked simulation where necessary |
| API result is accepted without verification | False success | Require post-action state verification and audit persistence |
| Unsupported browser blocks the application | Poor fallback experience | Feature-detect WebMCP and preserve full direct UI functionality |

## Implementation Plan

1. Confirm the Cloudflare deployment serves the actual AmbiOS application at the public URL.
2. Fix the D1 binding, apply the schema, and seed the challenge workspace.
3. Confirm explicit WebMCP registration on the deployed page.
4. Reduce or curate the public tools to the documented challenge workflow.
5. Verify one read-only call from ChatGPT Desktop.
6. Verify the approval-required path for the selected mutating action.
7. Verify execution, post-action state, audit record, and documentation proposal.
8. Repeat the same public-URL flow in Chrome with WebMCP enabled.
9. Capture the final tool list and evidence for the repository and challenge submission.
10. Record any simulated behavior and known browser limitations in the demo instructions.

## Acceptance Criteria

This ADR is considered implemented for the challenge when all of the following are true:

- A judge can open one public Cloudflare URL and see the AmbiOS application.
- The page registers the documented `ambios.*` WebMCP tools.
- ChatGPT can invoke at least one read-only tool successfully.
- The incident context and hot-fix recommendation are meaningful and tenant-scoped.
- A sensitive action is blocked until a human approves it through AmbiOS.
- The approved action is bounded, executed, verified, and recorded in the audit log.
- The direct UI remains functional without WebMCP.
- Chrome can reproduce the public discovery and safe invocation path.
- The repository documentation and demo video accurately describe the live behavior.
